| C1 mpv under Slint (OpenGL) | Windows 11 (AMD Radeon iGPU, 1920×1080 at 125%) | **PASS** | `experiments/c1-mpv-underlay`. libmpv-2.dll (client API 2.6) loaded at runtime with `libloading` 0.8 + a hand binding (`src/mpv.rs`); path from env `C1_LIBMPV`. Slint 1.18.1 default features + `unstable-winit-030`, chosen with `BackendSelector::new().backend_name("winit").renderer_name("femtovg")`; the GL context Slint gets on this PC is **OpenGL ES 3.2** (AMD driver) and mpv's GL renderer accepts it. Window 1280×720 logical = 1600×900 physical, transparent `background`, white 110px `Text` "Amazing grace". Checked by readback, not by eye: `glReadPixels` in `AfterRendering` once a second (full frame) and every frame (3 rows). Results, 10 s window after 2 s warm-up, recommended setting `MPV_RENDER_PARAM_BLOCK_FOR_TARGET_TIME=0`: `av://lavfi:testsrc2=size=1920x1080:rate=30` → 29.96–30.07 distinct video frames/s over 4 runs, est-frame-number rate 29.95–30.02, `estimated-vf-fps` 30, no frame drops inside the window (4–9 drops during the first 2 s of start-up), `vo-delayed-frame-count` 0, `hwdec-current` no (lavfi is raw video), CPU 30–52% of one core (2.5–4.3% of 12 logical CPUs). H.264 1080p30 file (made locally from testsrc2 with libmpv's encoder, `h264_mf`, 8 Mb/s) → 28.84–30.02 distinct frames/s over 4 runs (one run dropped 12 frames in the window while other agents were building), `hwdec-current` **d3d11va-copy** with `hwdec=auto-safe` (no zero-copy D3D11→GL path), CPU 33–46% of one core. Text: the same 55 181–55 184 pixels inside the text box were near-white (all channels ≥ 235) in every one of 10–11 samples while video under them changed; video-only corner mean luma ≈ 162, ≈ 12% of its pixels changed per second. Orientation checked with a red-top/blue-bottom lavfi source: top red, bottom blue with `flip_y = 1`. With the default blocking render (`BLOCK_FOR_TARGET_TIME=1`) it also plays (30.02–30.03 fps in 4 of 5 runs, one run 28.21 with 18 drops) but `mpv_render_context_render` then blocks the UI thread ≈ 27–31 ms per frame. **Gotchas for the implementer:** (1) Send `loadfile` only after `mpv_render_context_create` (i.e. from `RenderingSetup`); loading earlier fails with "No render context set" and mpv deselects the video track. (2) Slint's `get_proc_address` is only valid inside the notifier call; mpv uses it only during `mpv_render_context_create`, so passing a pointer to that closure as `get_proc_address_ctx` works. (3) `mpv_render_context_render` changed GL state: `GL_ACTIVE_TEXTURE` (TEXTURE1→TEXTURE0) and turned `GL_BLEND` off. FemtoVG 0.27 resets both at the start of each flush, so a run with no restore also passed, but the spike saves/restores program, VAO, array buffer, draw/read FBO, active texture + 2D textures on units 0–1, viewport, scissor/blend/cull/depth/stencil enables, blend func/equation, unpack alignment/row length/buffer. Keep the restore. (4) Render to the FBO bound at `BeforeRendering` (it was 0), size `window.size()` in physical pixels, `flip_y = 1`. Slint clears to the transparent background before `BeforeRendering`, so mpv must draw every Slint frame, not only on new video frames. (5) Update callback: runs on an mpv thread and must not call mpv. The spike coalesces with an `AtomicBool`, then `slint::invoke_from_event_loop` → `Weak::upgrade` → `window().request_redraw()`. With the non-blocking render, mpv asks for 42–60 redraws/s for 30 fps video, so Slint draws more often than needed. Calling `mpv_render_context_update` in the callback and only redrawing on `MPV_RENDER_UPDATE_FRAME` was not tried. (6) Free the render context in `RenderingTeardown` (GL current) before `mpv_terminate_destroy`, which blocks while a render context exists. The spike just exits the process. (7) With d3d11va-copy, redrawing the same frame gives ±1/255 differences (dither noise): harmless, but don't use exact pixel hashes to count frames. Note: CPU figures include the spike's own readbacks. Not tested: a real fullscreen 1920×1080 output, a second monitor, tearing (we can't see the screen; frame pacing came from mpv counters only). |

| C1 fallback (software) | Windows 11 | **PASS** | Same program with `--sw`: `renderer_name("software")`; mpv `MPV_RENDER_API_TYPE_SW`, format `rgb0`, into a 64-byte-aligned buffer (width rounded down to a multiple of 16, so stride is a multiple of 64), copied to a `SharedPixelBuffer<Rgb8Pixel>` and set as the `Image` under the text each new frame. Must use `BLOCK_FOR_TARGET_TIME=0`. testsrc2 1080p30 → 30.00–30.05 frames/s over 4 runs, 0 drops, mpv SW render 1.7–1.9 ms average into 1600×900, CPU 65–68% of one core in 2 timed runs (≈ 5.5–5.7% of 12 logical CPUs). H.264 file → 30.04–30.06 frames/s over 2 runs, 0 drops, `hwdec-current` d3d11va-copy, CPU 67–77% of one core (5.5–6.4%). `SLINT_DEBUG_PERFORMANCE=refresh_lazy,console` shows the software renderer presenting about 60 frames/s. Checked with `window().take_snapshot()` once a second: the same 51 312–51 314 text pixels were white in every sample over moving video. **Gotcha:** with the default blocking render, calling `mpv_render_context_render` from `invoke_from_event_loop` keeps the UI thread busy: mpv rendered about 29 frames/s, but Slint never painted and its timers never fired (watched for 100 s). Rendering from the event loop needs `BLOCK_FOR_TARGET_TIME=0` or a separate render thread. The software renderer has no rendering notifier, so the frame count is images handed to Slint. |
